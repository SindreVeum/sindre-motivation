# Aker Scholarship — Interactive Motivation Letter

A scroll-driven "living manuscript" built with vanilla Three.js + Vite. No framework — one big `story.js`, one `index.html`, one `styles.css`. The full creative brief lives in `aker_interactive_motivation_letter_plan.md`; read that for tone/intent, this file for how the code actually works and how to change it safely.

Run it with `npm run dev` (Vite dev server, usually on :5173).

## The core mental model

Everything is driven by a single number: `progress` (a `let` in `story.js`). Scroll position maps to `progress` via `cuePoints`, built from every element in `index.html` with a `data-progress="X"` attribute. `storyProgress()` linearly interpolates between the two nearest cue points for the current `scrollY`. `progress` itself *smoothly chases* `targetProgress` each frame (`progress += (targetProgress - progress) * .075`), so it lags scroll slightly — that's intentional (see gotcha below).

Every visual thing — node position, opacity, scale, camera framing, edge growth — is a pure function of `progress`, recomputed every frame in `render()`. There's no persistent animation state beyond node home/rootHome/rootAt-type precomputed values; if you know `progress`, you can derive the whole scene.

`range(value, start, end)` is the workhorse: a smoothstepped 0→1 ramp between two progress values. Chain multiplications of `range(...)` calls to build up "on during this window, off during that one" logic. `clamp` and `smooth` back it; `easeOutBack` gives a bouncy overshoot for "pop into existence" moments.

## Node system

`rawNodes` is one big array of plain objects (`{ id, type, p or offset, at, label?, color? }`), turned into `nodes` (a `Map`) with real Three.js sprites. `type` drives almost all behavior:

- **`self`** — Sindre, one node, `p:[0,0,0]`.
- **`trait`** — the early orbiting adjective nodes (age, curious, etc.), absorbed into Sindre early on.
- **`person`** — the `p1`–`p14` "people" nodes. Reused twice: first as the colorful "world gets bigger" burst (progress ~1.6–2.1, positions generated by `personNodes` via the shared `noise()` scatter — **don't hand-type 14 separate literals**, extend the scatter formula instead), then later as the Lisbon/Paris/Berlin "roots" (repositioned via `rootHome`, computed once at module load from `noise()`).
- **`place`** — Lisbon/Paris/Berlin. **Must stay exactly colinear with Sindre at x=0,z=0** — they're excluded from the z-diversity pass (see below) because that line is the rotation axis (see "The spine rotation").
- **`hub`** — the single "people" node. Its `.home` is screen-tracked: `placeHub()` raycasts from the `.people-word` DOM element's screen position while `progress` is in `[3.4, 3.96]`, then freezes forever after. Everything anchored "to the hub" (springs) reads `hub.home` fresh each frame.
- **`spring`** — Zypp/Norway/BI/PhD, offset from `hub.home`.
- **`idea`** — math/statistics/data/economics, offset from **Sindre's current (rotated) sprite position**, not the hub — this is the "second branch off Sindre" pattern (see below).
- **`finance`** — offset from `financeCenter`, a `THREE.Vector3` that gets `.set()` fresh every frame to `sindre.sprite.position + (0, FINANCE_LIFT, 0)` — i.e. it also branches off Sindre, but *above* him (ideas branch below). Do not confuse this with the old design where finance had fixed absolute `p:` coordinates deep below the origin — that's gone.
- **`ai`** — still uses the old fixed-`deep`-coordinate absolute-position system (`aiCenter`, `deep = -11`). Deliberately **not** reanchored to Sindre — the camera path from progress 7–11.8 is a long, heavily hand-tuned sequence (collision, purpose, ending) built around these absolute coordinates. Re-anchoring it would be a much bigger job than it looks; don't do it casually.
- **`future`**, **`anchor`** — the very end (research/industry/build, purpose).

### The "grows out of X" pattern

Used repeatedly (springs out of hub, ideas out of Sindre): in `formation()`, return `{ amount: range(progress, node.at, node.at+.22), source: <anchor node's current sprite.position or .home> }`. `node.sprite.position.lerpVectors(source, node.home, amount)` then does the actual travel. The **anchor logic lives in `updateNodes()`**: `if (node.offset) node.home.copy(anchor).add(node.offset)`, where `anchor` is chosen per-type (`sindre.sprite.position` for idea, `financeCenter` for finance, `hub.home` for spring). If you add a new "branches off Y" cluster, follow this exact shape — don't reinvent it.

**Ordering matters**: anchors that read another node's *live sprite position* (not `.home`) only work because JS `Map` iteration follows insertion order, and the source node (Sindre, index 0) is processed earlier in the same frame's loop than anything reading it. If you add a new anchor source, make sure the source node is defined earlier in `rawNodes` than anything that reads its `sprite.position`.

### Z-diversity pass

Right after `rawNodes` is defined, a block nudges any duplicate z-values apart (`seenZ` Set + deterministic `noise()` nudge) so no two nodes share a depth — this matters for the spine rotation to have real parallax, and gives nodes varied apparent size under perspective. **Lisbon/Paris/Berlin/Sindre (`spineIds`) are excluded** — don't remove that exclusion, it'll break the rotation axis.

## The spine rotation

Sindre + Lisbon + Paris + Berlin are colinear (x=0, z=0) — that line is a literal rotation **axis**, not just a pivot point. In `updateNodes()`, for node types in `rotatePivotTypes` (`self`, `place`, `person`):

1. **`flip`** (progress 3.96–3.995, fast): a Z-axis rotation around `pivot = hub.home` that lays the vertical column down into a horizontal "branching timeline" — Sindre ends up off to one side. Also computes `spineAxis` (the flipped direction from pivot to Sindre) fresh each frame.
2. **`spin`** (progress 3.96–4.3, slower): an *additional* rotation around `spineAxis` itself. Because it's rotating around the line, points **on** the line (Sindre/Lisbon/Paris/Berlin) don't move — only the off-axis "root" nodes sweep around it. This is deliberately a separate, slower window from `flip`: cramming both into the same fast window made things swing several z-units in an eyeblink, which read as things "disappearing" rather than rotating (a real bug we hit — see gotchas).
3. **`turn`** (progress 4.98–5.36): the same spine-axis spin, continuing later during "the funny thing is..." while the camera revisits Sindre.

If you need "more 3D-ness" somewhere, prefer adding another spine-axis-relative rotation phase over introducing a new arbitrary axis — arbitrary axes move the "fixed" reference points and break camera framing that assumes they're stationary.

## Camera

`cameraFrames`: a big hand-authored array of `{ at, p (position), t (target), view, roll? }` keyframes. `interpolateFrames()` picks the surrounding pair and lerps (or catmull-rom splines them, for progress 7–11.8). **These are hardcoded absolute-ish coordinates**, not computed from node positions — when a node's real position depends on `hub.home` (which is screen-tracked, not a fixed constant), the camera frame is only an *approximation* of where that node will actually be. This has caused mild mis-framing before (camera slightly off Sindre/Lisbon). If a reader complains the camera isn't quite centered on something, this is almost always why — nudge the frame's `p`/`t` values, don't assume the node itself is misplaced.

## Edges

`rawEdges`: `[fromId, toId, at, cross?, curved?, span?, weight?]`. In `updateEdges()`:
- **`amount`** = growth fraction (drives line *length*, endpoint lerp).
- **`reveal`** = a *faster* sub-window of the same span (`span * .3`) driving opacity. Keeping these separate is what makes lines look like they're growing out of a node rather than fading in at full length already-drawn.
- Every edge is actually **two overlapping `THREE.Line`s** ("strands"), the second offset by a small vector perpendicular to both the line and the camera's view direction (`edgeThickness = .028`). This is the standard workaround for WebGL ignoring `LineBasicMaterial.linewidth` — same trick the bubble rings already used (search "strands" in the file). If you add a new kind of line/edge, give it two strands too, or it'll look thin/flickery next to everything else.
- Once formed, **nothing fades back out** — no node or edge should drop to a lower opacity "in the background" once it's done being relevant. We tried a "recede into the background" ghosting design and reverted it; it read as things randomly disappearing. If you're tempted to dim something that's "done," don't — let it just sit there, or converge it into `purposeCenter` at the very end like everything else does.

## Text/DOM conventions

- `.beat` spans get large scroll-driven gaps by default (`.story-section .beat + .beat`, often overridden per-section). To group sentences tightly with **no** gap, add `.tight` to the later one(s) — it drops the gap to `1.6em` (normal paragraph spacing). Don't zero out a whole section's gap rule if you only want *some* sentences grouped; that collapses sentences you didn't mean to touch.
- **When you remove a big gap, shrink the section's `min-height` proportionally.** The gap was baked into that height; deleting the gap without shrinking the section leaves a long dead stretch of scroll where nothing changes before the next section starts. (We hit this after grouping the finance/generative/collision/responsibility sections — always check the section right after your edit for a dead zone.)
- No `.passage::before` halo backgrounds anymore — they were removed globally because they visually washed out graph nodes rendered behind text. Don't reintroduce a text backdrop unless explicitly asked.

## Verifying changes (important — read before testing)

There's no test suite; verification is "read the code, then check it renders right." Two ways to check, with a real gotcha in the middle:

**Direct state inspection (preferred, reliable):** temporarily add
```js
window.__debug = { nodes, edges, camera, financeCenter, setProgress: v => { targetProgress = v; progress = v; render(); } };
```
right before `function render(time = 0) {` in `story.js`, then drive it from an external tool (`agent-browser` CLI, installed via `npx agent-browser`) with `eval`, e.g. `__debug.setProgress(5.1); JSON.stringify(__debug.nodes.get('math').sprite.position)`. **Always remove the `window.__debug` line before finishing** — it's a debug-only shim, not project infrastructure.

**The scrollIntoView/hub.home gotcha:** `placeHub()` only updates `hub.home` while `progress` is inside `[3.4, 3.96]`, by raycasting the *actual current DOM layout* of `.people-word`. If you jump `scrollY` in one big instant hop (`scrollIntoView`, or setting `scrollTo` far away) while `progress` is still smoothing up from wherever it was, `progress` sweeps through `[3.4, 3.96]` on several animation frames *while the page is already scrolled to its final, far-away position* — so the raycast reads completely the wrong screen position and corrupts `hub.home` for the rest of the session. Everything downstream (Sindre's rotated position, the whole spine, financeCenter) is silently wrong after that. Two ways around it: use `__debug.setProgress()` to jump directly to a progress value *outside* `[3.4, 3.96]` (skips `placeHub` entirely, keeps the clean default `(0, -6.4, 0)`), or scroll gradually in many small steps with real waits between them if you specifically need to test the hub-tracking window itself. Real users scrolling normally never hit this — it's purely a fast-testing artifact, but it's fooled us more than once into "fixing" a phantom bug, so check for it before trusting a weird-looking screenshot.

**Screenshot check:** `npx agent-browser open http://localhost:5173/`, then `eval` + `screenshot` for visual confirmation. `npx agent-browser console` catches JS errors. `npx agent-browser close` when done. Remember `history.scrollRestoration = 'manual'` + `scrollTo(0,0)` after a `location.reload()` if you want a clean start — browsers restore prior scroll position on reload otherwise, which combines with the gotcha above in confusing ways.

## When making changes generally

- Match the existing style: terse, dense, comment only the non-obvious *why* (there's a comment on nearly every "clever" line in this file — that's the house style, keep it up).
- Prefer one shared formula/constant over many hand-typed near-duplicate literals (see `personNodes`, `noise()`) — it's both less code and easier to keep visually consistent when you need to retune it later.
- This is a personal, one-off creative piece being iterated on live with the author watching results — small, verifiable, reversible changes beat big speculative rewrites. When a change has real downstream risk (like reanchoring the AI/finance system would), say so before doing it rather than discovering the breakage after.
